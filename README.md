# IR-Sauron
<img width="543" height="544" alt="image" src="https://github.com/user-attachments/assets/303726ef-2fab-4bac-89e9-656fac24bf8d" />

IR-Sauron — платформа для команды реагирования на инциденты информационной безопасности (SOC/IR): от первичного приёма алертов до подтверждённого и задокументированного инцидента. Она покрывает весь цикл расследования — очередь триажа алертов, эскалацию в инцидент (в том числе массовую), реконструкцию графа связей между событиями атаки, разметку по MITRE ATT&CK с автоматическим повышением критичности и формирование итогового отчёта.

Помимо самого расследования, платформа даёт инструменты для поиска закономерностей: корреляционный граф в разделе «Анализ», сводную статистику по алертам и KQL-подобный язык запросов, одинаково работающий в разделах «Алерты», «Инциденты», «Статистика» и «Анализ». Роли и права, журнал действий, интеграция с внешними источниками алертов (Elastic, TheHive, JSON API, IMAP, файлы) и демо-режим с синтетическими данными настраиваются в панели администрирования.

Вход при первой установке admin /admin.
На скриншотах показана тема обороны Мордора, как если бы в нем была служба ИБ.

## Алерты

**Очередь триажа** — список входящих алертов со статусами Новый / В работе / Эскалирован / Отклонён / В архиве. Фильтр по статусу — мультивыбор чекбоксами, плюс фильтр по критичности; поиск (см. «Поиск (KQL)» ниже) по дате, статусу и описанию; постраничная навигация (50/100/200/500 на странице).

**Карточка алерта** — показывает разобранные URL/IP-адреса/учётные записи/файлы (из структуры ECS для Elastic-источников или эвристически из текста) и исходный индекс Elasticsearch, если алерт пришёл оттуда.

**Эскалация** — один алерт превращается в новый инцидент кнопкой «Эскалировать», несколько выделенных — кнопкой массовой эскалации в один инцидент. Критичность инцидента при эскалации нескольких алертов берётся как максимальная среди них.

**Назначение** — кнопка «Назначить» (одиночная или массовая) открывает список пользователей с быстрым вариантом «Взять себе»; назначенный отображается в столбце «Назначено».

**Тэги** — свободные текстовые метки на алерте, редактируются вручную в карточке алерта или назначаются автоматически правилом.

**Мягкое удаление и архив** — удаление алерта требует обязательного указания причины (кнопка подтверждения неактивна, пока причина не заполнена). Удалённые алерты попадают в архив с возможностью восстановления; статус «В архиве» — отдельный от «Отклонён» и тоже не требует дополнительных действий.

**Похожие алерты** — панель в карточке алерта показывает другие алерты с тем же внутренним IP-адресом или учётной записью — помогает быстро увидеть, не часть ли это уже известной активности.

**Правила алертов** — действие (подавить, эскалировать, перевести в архив или назначить тэг) выбирается выпадающим списком и применяется к новым алертам по условиям (источник, критичность, подстрока в заголовке/описании) — как для вручную созданных алертов, так и для подтянутых по расписанию из внешних источников. Правило можно создать прямо из выделенных алертов — форма заранее показывает, сколько алертов уже подходит под условия.

**Авто-повышение критичности по MITRE ATT&CK** — если в заголовке/описании алерта (или в ECS-полях `threat.tactic.name` / `threat.technique.id` для Elastic-источников) упоминается тактика или техника MITRE ATT&CK, критичность алерта может быть автоматически повышена до уровня, соответствующего этой тактике — подробная методика и таблица соответствия описаны в разделе «Инциденты» ниже. Понизить критичность так нельзя — только повысить.

## Инциденты

**Список инцидентов** — единый статус (Открыто → В работе → Подтверждён / Отклонён, фильтр — мультивыбор чекбоксами), критичность, гриф конфиденциальности; поиск (см. «Поиск (KQL)») по номеру, названию, IOC, IP-адресам, учётным записям и файлам; постраничная навигация с настраиваемым размером страницы.

**Критичность и гриф конфиденциальности** — критичность: Критический / Высокий / Средний / Низкий. Гриф: уровень 1–4 (зелёный / жёлтый / оранжевый / красный). Задаются при создании инцидента или наследуются от эскалируемого алерта; могут быть автоматически повышены по методике MITRE ATT&CK.

**MITRE ATT&CK и авто-повышение критичности** — при добавлении факту или связи графа тактики/техники MITRE ATT&CK (поле «Тактика» — название вроде «Credential Access», либо ID техники вроде «T1566» в поле «Техника») система по каждой упомянутой тактике определяет уровень серьёзности и — если он выше уже установленного — поднимает Критичность и Гриф инцидента до этого уровня. Понизить критичность или гриф автоматически нельзя — только повысить; аналитик всегда может изменить значение вручную после. Сопоставление тактик с уровнями и полная матрица — в разделе «MITRE ATT&CK» верхнего меню. Берётся максимальный уровень среди всех тактик, встреченных в инциденте, а не среднее. Каждое такое авто-повышение фиксируется в Логе действий панели администрирования.

**Назначение и присоединение** — кнопка «Назначить» открывает список пользователей (первая строка — «Назначить на себя»). Кнопка «Присоединить» связывает текущий инцидент с другим — при этом выбирается, какой из двух становится главным, и указывается причина; у присоединённого инцидента появляется подраздел «Инциденты» со ссылкой на главный (или список присоединённых, с возможностью отсоединить), а на вкладках «Алерты», «Таймлайн», «IOC» и «Граф» главного инцидента дополнительно показывается содержимое всех присоединённых, с пометкой, из какого инцидента что пришло.

**Архивирование и удаление** — инцидент нельзя удалить напрямую: сначала его нужно перевести в архив, и только оттуда удалить, с обязательным указанием причины.

**Таймлайн** — список фактов (событий) инцидента с типом события, уровнем достоверности и разметкой по MITRE ATT&CK (тактика/техника/подтехника).

**Граф** — конструктор связей между фактами: узлы — сетевое соединение, событие логона, операция с файлами, выполнение команды. Соединение двух узлов открывает форму создания связи с полями «Тип связи», дата/время перехода и техника MITRE. Расположение узлов сохраняется между визитами, новые узлы автоматически выстраиваются по причинно-следственной глубине связей.

**IOC и артефакты** — индикаторы компрометации (IP, домен, URL, хэш, email, имя файла) и файлы-доказательства с WORM-защитой (без возможности перезаписи после загрузки).

**Отчёт** — двухколоночная вкладка отчёта по инциденту. Авто-заполняемые блоки (не требуют ручного ввода): сводка, ключевые метрики MTTD/MTTR, хронология событий, сопоставление с MITRE ATT&CK, таблицы IOC и приложений-доказательств. Редактируемые разделы: анализ атаки, затронутые активы, оценка ущерба, реагирование и меры, выводы и рекомендации, свободный текст отчёта. Кнопка «Выгрузить в PDF» формирует печатную версию.

**Комментарии** — обсуждение конкретных фактов внутри инцидента, видимость — внутренняя или «в отчёт».

**Экспорт в JSON** — полная выгрузка инцидента (факты, связи, IOC) для передачи во внешние системы или архивирования.

## MITRE ATT&CK

**Матрица тактик и техник** — полная матрица Enterprise ATT&CK (актуальная версия) — тактики колонками, техники внутри. Данные синхронизируются автоматически по расписанию из официального репозитория MITRE; в настройках синхронизации видны источник (URL), время и статус последнего обновления.

**Легенда** — таблица соответствия тактик уровням критичности и грифа конфиденциальности (используется движком авто-повышения), отсортированная по убыванию критичности.

## Статистика

**Карточки статистики** — сводка по алертам за выбираемый период (24 часа по умолчанию, текущая неделя, 7 дней, текущий месяц, 30 дней, произвольный «Период»): график количества по времени, разбивка по статусам и типам угроз, топ URL, внешних и внутренних IP-адресов, учётных записей и файлов, встречающихся в алертах.

**Отчёт для SOC-аналитика** — печатная версия сводки: диаграмма динамики по времени с подписанными значениями над каждым столбцом, текстовая сводка периода, детализация по каждому типу угрозы (с топ-5 связанных IP-адресов и учётных записей под каждым типом), и те же таблицы топ URL/IP/аккаунтов/файлов. Кнопка «Выгрузить в PDF» формирует печатный документ.

**Поиск по таблицам** — поле поиска (см. «Поиск (KQL)» ниже) фильтрует одновременно обе части раздела — таблицы карточек статистики и таблицы в печатном отчёте.

## Анализ

**Граф корреляций** — связи между алертами по общим внутренним/внешним IP-адресам, учётным записям, файловым операциям и структурированным IOC (домены/URL/хеши/email). Строится по поисковому запросу (см. «Поиск (KQL)»), в том числе по имени алерта или инцидента, а не автоматически при открытии раздела.

**Фильтры над графом** — чекбоксы по каждому типу элемента (алерты, IP, учётные записи, файлы, IOC) и отдельно — по принадлежности алерта инциденту (в инциденте/без инцидента, со счётчиком).

**Группировка и связи** — похожие алерты (совпадающие по одному и тому же набору сущностей) сворачиваются в один узел со счётчиком, чтобы не загромождать граф; связи внутри цепочки из 3 и более элементов отображаются жирнее обычных.

**Панель деталей** — клик по узлу открывает правую панель вместо перехода на другую страницу: описание алерта, таблицу упоминаний сущности в алертах, либо список похожих алертов группы с разбивкой совпадений по типам. Алерт из любого списка в панели можно прочитать прямо там же, не покидая анализатор.

**Расположение узлов** — узлы можно перетаскивать мышью — связанные линии тянутся следом; кнопка «Автораскладка» заново пересчитывает физическую раскладку графа (расстояние между узлами настроено так, чтобы подписи не наезжали друг на друга).

**Кнопка «В анализ»** — есть на карточке алерта, в списке алертов инцидента и в панели IOC — сразу открывает раздел «Анализ» с готовым запросом по выбранному IP/учётной записи/файлу.

## Поиск (KQL)

**Синтаксис** — поле поиска в разделах «Алерты», «Инциденты», «Статистика» и «Анализ» понимает небольшой язык запросов в духе KQL: операторы `AND`, `OR`, `NOT` (регистр не важен), скобки для группировки, `"точная фраза в кавычках"` и маска со звёздочкой (`*`) для начала/середины/конца значения. Несколько слов без операторов между ними считаются соединёнными через `AND`, поэтому обычный поиск в одно-два слова продолжает работать как раньше. При синтаксической ошибке в запросе фильтр не применяется (показываются все строки), а под полем появляется пояснение, что именно не так с запросом.

Примеры:

- `"192.168.100.12" AND NOT (*.mordor.local OR freepeople.local)` — точное значение 192.168.100.12, но с исключением всего, что относится к домену mordor.local в любом виде (`*.` означает «оканчивается на») или содержит freepeople.local.
- `*.internal` — всё, что оканчивается на `.internal`, например внутренние домены и адреса.
- `critical OR "access denied"` — строки, где встречается слово critical, либо точная фраза access denied.

По каким полям ищет:

- **Алерты** — дата создания алерта, метка статуса (например «Новый», «Эскалирован») и описание.
- **Инциденты** — название инцидента, номер (ID) инцидента и значения IOC, привязанных к инциденту (IP, домен, URL, хэш, email, имя файла). Поиск выполняется на сервере, а не только среди уже загруженных на текущей странице записей.
- **Статистика** — значения в таблицах топ URL, внешних и внутренних IP-адресов, учётных записей и файлов, а также в детализации по каждому типу угрозы — запрос вводится один раз и применяется сразу ко всем этим таблицам, каждая строка проверяется по своему значению.
- **Анализ** — название алерта, название связанного с ним инцидента, а также значения IP-адресов, учётных записей, файлов и IOC, отображаемых на графе связей.

## Роли и права

**Роли** — администратор, руководитель IR, аналитик, наблюдатель, внешний подрядчик, демо (служебная роль демо-режима — видит все инциденты, доступ только на чтение, права зафиксированы и не редактируются).

**Матрица прав** — права на конкретные действия (создание/редактирование инцидентов, управление пользователями, доступ к источникам алертов и т.д.) настраиваются для каждой роли в разделе «Роли пользователей» панели администрирования. У администратора доступ всегда полный — это защищает от случайной блокировки собственного доступа.

## Панель администрирования

**Пользователи** — создание, редактирование, деактивация и активация учётных записей.

**Роли пользователей** — настройка матрицы прав по ролям (см. раздел «Роли и права» выше).

**Источники алертов** — подключение Elastic, TheHive и произвольного JSON REST API по API-ключу (учётные данные шифруются в базе), почтового ящика по IMAP, а также «Слежение за папкой» — периодический опрос локальной/примонтированной папки с CSV- или NDJSON-файлами. Автоматический периодический опрос по расписанию плюс синхронизация по кнопке «Синхронизировать сейчас».

**Слежение за папкой: инкрементальное чтение больших файлов** — для CSV и NDJSON каждый файл читается не целиком при каждом опросе, а начиная с байтового смещения, сохранённого после предыдущего чтения, — поэтому уже прочитанные гигабайты не перечитываются и не расходуют память повторно. Идентификатор алерта строится из имени файла и байтового смещения строки (а не из времени изменения файла), поэтому дозапись новых строк в конец растущего файла не создаёт повторных алертов для уже обработанных строк — повторно обрабатывается только реально добавленная часть. Единственное исключение — файл в формате одного большого JSON-массива: он не поддаётся дочтению по смещению и перечитывается целиком при каждом изменении, поэтому для больших выгрузок предпочтительны CSV или NDJSON.

**JSON API: пагинация и инкрементальная синхронизация** — в настройках источника можно задать параметры номера/размера страницы (тогда данные забираются постранично вместо одного запроса) и параметр «с даты» — если сам API его поддерживает, каждый следующий опрос запрашивает только новые записи. Ответ читается ограниченными по размеру частями, а не буферизуется целиком без лимита.

**Уведомления** — настройка отправки на почту и в Telegram-бота.

**Часовой пояс** — выбор из списка с указанием разницы в часах для каждого варианта.

**Бэкапы и восстановление** — зашифрованные паролем бэкапы конфигурации и базы данных. Восстановление показывает индикатор прогресса, а на время восстановления базы данных приложение переходит в режим техобслуживания (страница-заглушка для всех пользователей).

**Лог действий** — изменения настроек панели администрирования и факты удаления инцидентов/алертов, с фильтром по типу объекта, действию и пользователю.

**Демо-режим** — один переключатель одновременно включает оранжевую плашку «РЕЖИМ DEMO» в шапке для всех пользователей и блок с учётными данными на странице входа, гарантируя активную учётную запись demo/demo с доступом только на чтение. Отдельные кнопки заполняют базу демо-данными (алерты и инциденты, равномерно распределённые по техникам MITRE ATT&CK), демо-источниками алертов и демо-записями лога действий, либо полностью очищают все алерты и инциденты в системе (с обязательным вводом фразы подтверждения).

## Публичные точки входа

**Режим разработки** — frontend доступен напрямую на `http://localhost:3000` (Vite dev-сервер с горячей перезагрузкой), backend API — на `http://localhost:8000`.

**Продуктивный режим** — единая точка входа — `http://localhost`, автоматически перенаправляется на `https://localhost` (443). TLS завершается на Nginx, который проксирует запросы к frontend и backend внутри Docker-сети.

**Относительные пути на фронтенде** — все запросы браузера к API (`/api/v1`) и WebSocket (`/ws`) идут по относительному пути — конкретный хост подставляется автоматически из текущего адреса страницы, поэтому в коде фронтенда нигде не зашит конкретный домен или порт.

## Темы оформления

**Светлая / Тёмная / Саурон / Трандуил** — переключаются в профиле пользователя. «Саурон» и «Трандуил» — тематические пасхалки: в «Сауроне» статус инцидента в списке и карточке отображается иконкой Ока, в «Трандуиле» — иконкой листа. У каждой темы своя надпись-водяной знак в верхнем меню и свой favicon вкладки браузера.
## Стек технологий

- **Backend**: FastAPI (Python), SQLAlchemy (async), PostgreSQL, Redis, MinIO (S3-совместимое хранилище артефактов), WebSocket для совместной работы в реальном времени.
- **Frontend**: React + TypeScript, Vite, Zustand.
- **Инфраструктура**: Docker Compose, Nginx, опционально Keycloak/OIDC для SSO.

## Быстрый старт

```bash
cp .env.example .env
make dev     # dev-стек с hot-reload
# либо
make up      # production-стек
```

Frontend будет доступен на `http://localhost:3000` (dev) или через Nginx на `http://localhost` (production).

## Требования к установке

- **Docker** 24+ и **Docker Compose** v2 (команда `docker compose`, а не устаревший отдельный `docker-compose`).
- Linux-хост (проверено на Debian/Ubuntu) или Docker Desktop (Windows/macOS) для локальной разработки.
- Свободные порты **80** и **443** на хосте (Nginx) — либо переназначьте их в `docker-compose.yml`.
- Ориентировочно не менее **2 vCPU** и **4 ГБ RAM**, **10 ГБ** свободного места на диске — для тестового стенда с небольшим объёмом данных; под боевую нагрузку ресурсы стоит считать исходя из реального объёма алертов и дел.
- TLS-сертификат в `nginx/ssl/cert.pem` и `nginx/ssl/key.pem` — по умолчанию самоподписанный для разработки, для продакшена замените на сертификат от доверенного CA.
- Заполненный `.env` (скопируйте из `.env.example`): как минимум пароли PostgreSQL/Redis/MinIO и `SECRET_KEY` для подписи JWT.
- Клиент `pg_dump`/`pg_restore` внутри backend-образа зафиксирован на версии **PostgreSQL 16** (через репозиторий PGDG) — под версию сервера `postgres:16-alpine` из docker-compose. При восстановлении бэкапа базы данными снаружи контейнера используйте клиент той же версии, иначе `pg_restore` может завершиться с ошибкой несовместимости.
